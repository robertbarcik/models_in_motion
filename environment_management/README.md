# Environment Management - Hands-On Tutorial

Welcome to the Environment Management module! This README contains all the commands and configuration examples from the tutorial, so you can follow along step-by-step.

## Why Environment Management Matters

Utilizing external packages is essential for modern data science. We don't want to build functions from scratch—we want to leverage robust, readily available packages. However, this requires careful consideration of which packages we select and how we manage their versions.

---

## 1. Choosing Packages Wisely

When selecting packages for your data science project, consider:
- **Backward compatibility** - Will updates break your code?
- **Release stability** - How often do breaking changes occur?

**Example comparison:**
- `scikit-learn` (Python) - Strong emphasis on backward compatibility
- `dplyr` (R tidyverse) - May introduce breaking changes between versions

**View release notes:**
- scikit-learn: https://scikit-learn.org/stable/whats_new.html
- dplyr: https://dplyr.tidyverse.org/news/index.html

## 2. Environment and Package Managers

### Key Concepts

| Tool | Type | Description |
|------|------|-------------|
| `venv` | Environment manager | Creates isolated Python environments |
| `conda` | Both | Environment + package manager |
| `pip` | Package manager | Installs Python packages (fast, less thorough) |

### Common Combinations

1. **venv + pip** - Lightweight, Python-only projects
2. **conda** - Complex projects, multi-language support

### Pip vs Conda: Key Differences

```
Pip:
- Installs dependencies in a recursive, serial loop
- No effort to ensure all dependencies are fulfilled simultaneously
- Fast but can create broken environments

Conda:
- Uses a SAT solver to verify all requirements
- Takes extra time but prevents broken environments
- Can be slow with complex environments
```

## 3. Pip Package Version Pinning

### Bad Practice (Don't do this)
```bash
# In your code - no version specified
pip install scikit-learn
```

### Better (For experimentation)
```bash
# At least pin the version
pip install scikit-learn==1.0.2
```

### Professional Approach (For deployment)

**Create a `requirements.txt` file:**
```txt
pandas==1.2.1
scikit-learn==1.0.2
numpy==1.21.0
```

**Install from requirements file:**
```bash
pip install -r requirements.txt
```

### Best Practice: Using pip-tools

**Step 1: Install pip-tools**
```bash
pip install pip-tools
```

**Step 2: Create `requirements.in` (your direct dependencies)**
```txt
pandas==1.5.2
scikit-learn==1.2.0
```

**Step 3: Compile to generate complete `requirements.txt`**
```bash
pip-compile requirements.in
```

This generates a `requirements.txt` with all transitive dependencies pinned:
```txt
# This file is autogenerated by pip-compile
joblib==1.2.0
    # via scikit-learn
numpy==1.24.1
    # via
    #   pandas
    #   scikit-learn
pandas==1.5.2
python-dateutil==2.8.2
    # via pandas
pytz==2022.7
    # via pandas
scikit-learn==1.2.0
scipy==1.10.0
    # via scikit-learn
six==1.16.0
    # via python-dateutil
threadpoolctl==3.1.0
    # via scikit-learn
```

**Why not just `pip freeze`?**
```bash
# This is less adequate for production
pip freeze > requirements.txt
```
- `pip freeze` merely lists what's installed without resolving dependencies
- `pip-tools` ensures versions work together when re-installed

## 4. Anaconda Environment (environment.yml)

### Basic Structure

Create an `environment.yml` file:

```yaml
name: my_env
channels:
  - defaults
dependencies:
  - python=3.8.15
  - numpy=1.23.5
  - pandas=1.3.5
  - scikit-learn=1.1.3
  - pip
  - pip:
    - requests==2.25.1
```

### Key Sections Explained

| Section | Purpose |
|---------|---------|
| `name` | Name of the conda environment |
| `channels` | Package sources (defaults, conda-forge) |
| `dependencies` | Conda packages with versions |
| `pip:` | Packages to install via pip (not in conda) |

### Searching for Packages

**Search in default channel:**
```bash
conda search package_name
```

**Search in specific channel (e.g., conda-forge):**
```bash
conda search package_name -c conda-forge
```

### Creating and Managing Environments

**Create environment from yml file:**
```bash
conda env create -f environment.yml
```

**Activate the environment:**
```bash
conda activate my_env
```

**Export current environment:**
```bash
conda env export > environment.yml
```

**List all environments:**
```bash
conda env list
```

**Remove an environment:**
```bash
conda env remove -n my_env
```

### Checking Package Compatibility

When mixing conda and pip packages, verify compatibility:

```bash
# Install compatibility checker
pip install pip-check

# Check for issues
pip-check
```

```bash
# Visualize dependencies
pip install pipdeptree
pipdeptree
```

## 5. Multiple Environments in a Single Project

It's common practice to have separate environments for different stages:

### Development Environment
For experimentation and exploration:

**requirements-dev.txt:**
```txt
-r requirements.txt
jupyter==1.0.0
matplotlib==3.6.0
seaborn==0.12.0
ipykernel==6.19.0
```

### Staging Environment
For validation and testing:

**requirements-staging.txt:**
```txt
-r requirements.txt
pytest==7.2.0
pytest-cov==4.0.0
```

### Production Environment
Minimal packages for deployment:

**requirements.txt (base):**
```txt
pandas==1.5.2
scikit-learn==1.2.0
flask==2.2.0
```

### Installing Different Environments

```bash
# Development
pip install -r requirements-dev.txt

# Staging
pip install -r requirements-staging.txt

# Production
pip install -r requirements.txt
```

## Quick Reference

### Virtual Environment Commands (venv)

```bash
# Create virtual environment
python -m venv myenv

# Activate (macOS/Linux)
source myenv/bin/activate

# Activate (Windows)
myenv\Scripts\activate

# Deactivate
deactivate

# Delete environment
rm -rf myenv
```

### Pip Commands

```bash
# Install package
pip install package_name

# Install specific version
pip install package_name==1.0.0

# Install from requirements
pip install -r requirements.txt

# Show installed packages
pip list

# Show package info
pip show package_name

# Upgrade package
pip install --upgrade package_name

# Uninstall package
pip uninstall package_name
```

### Conda Commands

```bash
# Create environment
conda create -n myenv python=3.9

# Create from yml
conda env create -f environment.yml

# Activate
conda activate myenv

# Deactivate
conda deactivate

# List environments
conda env list

# List packages in environment
conda list

# Install package
conda install package_name

# Install from specific channel
conda install -c conda-forge package_name

# Update package
conda update package_name

# Remove environment
conda env remove -n myenv

# Export environment
conda env export > environment.yml
```

## Best Practices Summary

1. **Always pin versions** - Never use `pip install package` in production
2. **Use pip-tools** - For deterministic, reproducible builds
3. **Separate environments** - Dev, staging, and production
4. **Version control** - Commit `requirements.in`, `requirements.txt`, and `environment.yml`
5. **Test after setup** - Always run your code after creating a new environment
6. **Document Python version** - Specify in README or use conda/pyenv
7. **Prefer conda packages** - When using conda, minimize pip packages for better dependency resolution
